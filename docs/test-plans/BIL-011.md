## Questions

> **Réponses (2026-11-13)** : les huit recommandations ci-dessous sont retenues telles quelles
> (délégation du développeur). Hypothèses H1 à H7 validées. Aucune question ouverte.

1. **Consommateur `ticket.rejected` de Paiements (prévu par le modèle, écarté par BIL-009).**
   Recommandation : **dans le ticket**. Le modèle (Paiements) l'exige et la garantie « un seul
   remboursement » de CA1 n'est vérifiable qu'avec les deux sources (`show.cancelled` puis
   `ticket.rejected` sur la même commande, motif `SEANCE_ANNULEE`). Le coût est faible : même
   passage conditionnel `ACCEPTE` → `REMBOURSE` et même publication que pour `show.cancelled`.
   Il ferme aussi le débit sans remboursement d'une commande `PLACE_DEJA_VENDUE`. L'e-mail de
   refus de Notifications sur `ticket.rejected` reste **hors ticket** : l'e-mail de remboursement
   (`payment.refunded`) prévient déjà l'acheteur.
2. **Course entre `POST /payments` et le consommateur `show.cancelled` de Paiements.** Le
   paiement peut lire `seances_annulees` vide, le consommateur insérer la séance et ne rien
   rembourser (paiement pas encore écrit), puis le paiement s'écrire `ACCEPTE` : débit jamais
   remboursé. Recommandation : verrou consultatif de transaction sur `seance_id`, partagé dans
   `creerPaiement` (`pg_advisory_xact_lock_shared`), exclusif dans le consommateur ; invariant
   testé : au terme de la course, soit 409 `SHOW_CANCELLED` sans ligne, soit un paiement
   `REMBOURSE` et un `payment.refunded`.
3. **Course entre l'émission (`order.confirmed`) et le consommateur `show.cancelled` de Billets**
   (laissée à ce ticket par BIL-009). Même trou : l'émission lit `seances_annulees` vide, puis
   écrit des billets `EMIS` après le passage `ANNULE`. Recommandation : même schéma de verrou
   consultatif sur `seance_id` (partagé à l'émission, exclusif à l'annulation) ; invariant :
   aucun billet `EMIS` de `S` une fois les deux traitements finis.
4. **`payment.refunded` reçu par Commandes pour une commande encore `EN_ATTENTE`** (paiement
   accepté puis remboursé avant que `payerCommande` ne confirme). Sans règle, la confirmation
   arrive ensuite et la commande reste `CONFIRMEE` alors qu'elle est remboursée. Recommandation :
   sous `FOR UPDATE`, `EN_ATTENTE` → `EXPIREE` (transition autorisée par le modèle) avec
   `order.expired` ; la confirmation conditionnelle de `payerCommande` échoue alors, sans
   `order.confirmed`. `EXPIREE` ou `REMBOURSEE` : message ignoré (journal `INFO`), jamais de DLQ
   (point 28 de la review BIL-002).
5. **Commandes, `show.cancelled` sur une commande `EN_ATTENTE` déjà envoyée à Paiements.**
   Recommandation : passage `EXPIREE` sans appel HTTP à Paiements et sans `remboursement_du` ;
   le remboursement est fait par le consommateur `show.cancelled` de Paiements (tous les paiements
   `ACCEPTE` de la séance). Les commandes `EN_ATTENTE` dont `expire_le` est NULL sont aussi
   expirées (passage gardé par `WHERE statut = 'EN_ATTENTE'`).
6. **Notifications reçoit `payment.refunded` (ou `show.cancelled`) avant `order.confirmed`, ou
   pour une commande jamais confirmée.** Le modèle dit : ligne absente = « pas encore reçu »,
   exception et nouvel essai. Recommandation : garder cette règle pour `payment.refunded`
   (exception `CommandeInconnue`, trois tentatives, puis DLQ ; limite écrite dans le README pour
   une commande jamais confirmée, cas de Q4). Pour `show.cancelled`, n'écrire qu'aux
   destinataires connus de `S` au moment du traitement ; un acheteur dont `order.confirmed`
   arrive après ne reçoit que l'e-mail de remboursement (limite écrite dans le README, pas de
   nouvelle table).
7. **« Chaque acheteur » : un e-mail par acheteur ou par commande ?** Recommandation : un e-mail
   d'annulation par commande de la séance (clé `UNIQUE (evenement_id, commande_id)` de `envois`),
   un e-mail de remboursement par `payment.refunded`.
8. **`remboursement_du: true` sur `order.expired` (BIL-008, BIL-010).** Le modèle ne fait pas de
   Paiements un consommateur de `order.expired`. Recommandation : **hors ticket** (ticket de
   suivi) ; le cas « séance annulée » est couvert par `show.cancelled` dans Paiements.

Hypothèses retenues (réponse dans les docs ou le ticket) :

- **H1** : le modèle l'emporte sur le ticket : `show.cancelled` passe `EN_ATTENTE` → `EXPIREE` (et
  `order.expired`) ; une commande `CONFIRMEE` attend `payment.refunded` pour passer
  `REMBOURSEE` ; aucun statut « annulée ».
- **H2** : contrôles de la route dans l'ordre du contrat : authentification (401), rôle `admin`
  et scope `events:write` (403), événement puis séance (404 `EVENT_NOT_FOUND`,
  `SHOW_NOT_FOUND`, aussi pour une séance d'un autre événement), puis 409
  `SHOW_ALREADY_CANCELLED` avant `SHOW_ALREADY_STARTED`. « Commencée » = `debut <= maintenant`,
  la définition déjà utilisée par Commandes (BIL-008).
- **H3** : `UPDATE seances SET annulee = true WHERE id = :s AND annulee = false` et
  `publier_plus_tard(show.cancelled)` dans la même transaction ; 0 ligne : 409. Cache invalidé
  après le commit : copies fraîches **et** de secours de `lireSeance`, `lireSeanceParId`, et
  génération `catalogue:generation:seances:<evenement_id>` incrémentée (`listerSeances`).
- **H4** : CA3 = billets de `S` au statut `ANNULE` en base (aucune route de lecture de billet
  n'existe ; `verifier_qr` reste un contrôle de signature, le scan V3 lira le statut). Places et
  billets `ANNULE` gardés (`uq_billets_place` sans condition, Q14 de BIL-006).
- **H5** : chaque consommateur passe par `consommateur_idempotent` (files
  `billets.show-cancelled`, `commandes.show-cancelled`, `commandes.payment-refunded`,
  `paiements.show-cancelled`, `paiements.ticket-rejected`, `notifications.show-cancelled`,
  `notifications.payment-refunded`) ; tout passage de statut est conditionnel au statut courant.
- **H6** : `payment.refunded` : `paiement_id`, `commande_id`, `seance_id`, `montant` du paiement,
  un par paiement remboursé, dans la transaction du passage `REMBOURSE`.
- **H7** : `infos_seances` n'est pas remplie (BIL-009) : les e-mails citent la séance par son
  identifiant, comme l'e-mail du billet ; aucune adresse ni jeton dans les journaux.
