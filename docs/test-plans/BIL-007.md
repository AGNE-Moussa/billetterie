# Plan de test : BIL-007, Test de concurrence : jamais deux ventes de la même place

- Ticket : `docs/tickets/BIL-007.md` ; contrat : `services/billets/openapi.yaml`
  (`PUT /api/v1/seats/{place_id}/lock`, `GET /api/v1/seats`)
- Niveaux : intégration (vrai PostgreSQL 16 et vrai Redis 7 par Testcontainers, contrainte du
  ticket ; aucun cas unitaire : rien de nouveau n'est testable sans base ni Redis)
- Règles : `.claude/rules/places-concurrence.md`, `.claude/rules/tests.md`,
  `.claude/rules/billets-qr.md` (aucune émission hors `ticketing.order.confirmed`)
- Fixtures réutilisées : `services/billets/tests/integration/conftest.py` (BIL-006) :
  `plateforme` (deux instances `billets-1` et `billets-2` sur la même base et le même Redis),
  `seance` (séance commune de 27 places), `base`, `observateur`, `outils.borne`.

## Questions

> **Réponses (2026-11-03)** : recommandations Q1 à Q10 retenues (délégation des validations).

1. **Ce que « vente » veut dire dans CA1.** Aucune route d'émission n'existe encore (l'émission
   viendra avec le consommateur de `ticketing.order.confirmed`, `billets-qr.md`). Recommandation :
   pour CA1, une « vente » est un verrou obtenu (200 sur `PUT .../lock`), comme le disent les
   étapes 1 et 2 du ticket ; la base (CA2) couvre l'étape suivante. Le test de bout en bout
   « verrou puis émission » sera ajouté par le ticket de l'émission, pas inventé ici.
2. **Forme des « dix exécutions de suite ».** Trois lectures : dix tours dans un même lancement
   de pytest, dix lancements de CI verts d'affilée, ou un greffon (`pytest-repeat`, nouvelle
   dépendance). Recommandation : `@pytest.mark.parametrize("execution", range(1, 11))`, ids
   `execution-01` à `execution-10`, dans un seul lancement ; chaque tour repart de fixtures
   neuves (base vidée, Redis vidé, nouvelle séance, deux nouvelles instances), et un tour rouge
   est nommé dans le rapport. Pas de nouvelle dépendance.
3. **Simultanéité réelle.** Les 100 appels partent par `asyncio.gather` vers `httpx.ASGITransport`
   dans une seule boucle (comme BIL-006, décision Q24) ; la concurrence réelle se joue dans Redis
   et PostgreSQL, qui sont de vrais processus séparés. Recommandation : garder ce montage, ajouter
   une barrière (`asyncio.Event`) levée une fois les 100 tâches créées, et vérifier côté client
   que les appels se chevauchent (le dernier départ précède la première réponse) pour qu'un test
   devenu séquentiel par accident échoue au lieu de passer à vide. Lancer de vrais serveurs
   uvicorn multiprocessus est plus fidèle mais plus lent et hors du montage existant ; à garder
   pour un ticket de charge si le développeur le souhaite.
4. **Nombre d'instances.** Recommandation : les deux instances du conftest (comme `billets-1` et
   `billets-2` de Compose), 50 appels chacune (`plateforme.instance(numero)`, modulo 2).
5. **Nombre de transactions simultanées pour CA2.** Chaque transaction tient sa propre connexion ;
   PostgreSQL 16 de Testcontainers accepte 100 connexions au plus (`max_connections`), dont
   certaines déjà prises (fixtures, superutilisateur réservé) : 100 insertions simultanées
   échoueraient sur « too many clients », pas sur la contrainte. Recommandation : N = 50
   connexions simultanées, configuration de PostgreSQL inchangée. Alternative : surcharger la
   fixture `postgres` du module avec `-c max_connections=200` pour N = 100.
6. **Répéter CA2 dix fois aussi.** Le ticket ne le demande que pour CA1. Recommandation : oui,
   même paramétrage que Q2 (une course de transactions est probabiliste, et le coût est de
   quelques secondes).
7. **Place de ces tests face à ceux de BIL-006.** `test_cinquante_verrouillages_simultanes_de_la_meme_place_n_ont_qu_un_gagnant`
   est un sous-ensemble strict du cas CA1 à 100 × 10, et
   `test_deux_billets_simultanes_sur_la_meme_place_sont_refuses_par_la_base` un sous-ensemble
   strict du cas CA2 à N transactions. Recommandation : supprimer ces deux cas de BIL-006 et les
   remplacer par ceux de BIL-007 dans un nouveau fichier
   `services/billets/tests/integration/test_concurrence_ventes.py` ; garder tous les autres cas
   de BIL-006 (places différentes, après expiration, confirmations, libérations concurrentes,
   `test_un_conflit_n_est_jamais_une_erreur_500` qui vérifie aussi l'absence de jeton dans les
   journaux, FK composite en séquentiel, `uq_places_seance_rang_numero`). Supprimer un test
   existant n'étant pas prévu par le ticket, la décision revient au développeur ; à défaut, les
   garder (doublon de quelques secondes).
8. **Garantir que le test tourne en CI.** Aujourd'hui le job `integration` lance
   `make test-integration`, qui ramasse `services/*/tests/integration` : un nouveau fichier y
   tourne déjà, mais rien n'empêche qu'il soit un jour sauté ou désélectionné sans bruit.
   Recommandation : (a) déclarer un marqueur `concurrence` dans `[tool.pytest.ini_options]
   markers` du `pyproject.toml` et marquer le module (`pytestmark = [pytest.mark.anyio,
   pytest.mark.concurrence]`) ; (b) ajouter une cible `make test-concurrence`
   (`uv run pytest services/billets/tests/integration -m concurrence`) et une étape nommée
   « Concurrence des places (BIL-007) » dans le job `integration` ; pytest sort en code 5 quand
   aucun test n'est collecté, donc l'étape échoue si le marqueur ou le fichier disparaît ;
   (c) exclure ces tests de l'étape générale (`-m "not smoke and not concurrence"`, car un `-m`
   en ligne de commande remplace celui d'`addopts`) pour ne pas les jouer deux fois ;
   (d) vérifier que le check `integration` est obligatoire dans la protection de `main`
   (réglage GitHub, hors dépôt, à confirmer par le développeur).
9. **Budget de durée en CI.** Estimation : conteneurs du module démarrés une fois (environ 10 s),
   10 tours de 100 appels en processus (1 à 3 s chacun), 10 tours de N insertions (moins de 1 s
   chacun) : moins d'une minute de plus pour un job borné à 20 min. Recommandation : chaque tour
   borné par `outils.borne` (60 s, délai du conftest), durée réelle relevée par
   `--durations=10` dans l'étape dédiée ; pas de changement du `timeout-minutes` du job.
10. **Une erreur 503 sous la charge.** Chaque instance reçoit 50 appels simultanés pour un pool
    SQLAlchemy par défaut (5 + 10 connexions, attente de 30 s) et un délai Redis borné
    (`delai_redis`) : un `BaseIndisponible` ou `VerrouIndisponible` (503) reste possible.
    Recommandation : tout 5xx fait échouer le test (règle « jamais une erreur 500 » et consigne
    du ticket) ; si cela arrive, c'est un constat à remonter (dimensionnement du pool), pas une
    raison d'allonger les délais dans le test.
