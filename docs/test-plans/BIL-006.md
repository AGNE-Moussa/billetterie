- Ticket : `docs/tickets/BIL-006.md` (section « Décisions (validation du contrat, 2026-11-02) »,
  Q1 à Q8, qui fait foi sur la page Notion) ; contrat : `services/billets/openapi.yaml`
  (`sante`, `listerPlaces`, `verrouillerPlace`), recopié de `docs/contrats/billets.yaml` ;
  événement : `docs/evenements/ticketing.show.scheduled.json` ; modèle : `docs/modele-donnees.md`

  PostgreSQL 16, Redis 7, RabbitMQ, Consul, Traefik)

Ticket back : pas de niveau `composant` ni `parcours`. Le ticket touche Billets : chaque critère
lié aux places porte au moins un cas de concurrence en intégration, avec un vrai Redis et de
vraies requêtes simultanées.

Q8 ») ; les questions de ce plan continuent à partir de **Q9**, pour éviter toute confusion.

Les trois CA ne couvrent pas les étapes, la contrainte ni les décisions. Comme pour BIL-004,
elles deviennent des critères dérivés E1 à E9, chacun rattaché à un texte du ticket, du contrat,
du modèle ou des rules.

## Questions

> **Réponses (2026-11-02)** : toutes les recommandations Q9 à Q24 sont retenues (délégation des
> validations par le développeur). Q9 à Q11 complètent le contrat : `503 VERROU_INDISPONIBLE`
> (Redis injoignable) sur `verrouillerPlace` et `listerPlaces`, `503 BASE_INDISPONIBLE` sur les
> deux routes.

9. **Redis injoignable pendant un verrouillage.** Le contrat ne déclare pas de 503 sur
   `verrouillerPlace`. Recommandation : échec fermé, jamais de 200 sans verrou posé ni de 500 ;
   `503` avec un code technique dédié (proposition : `VERROU_INDISPONIBLE`), appel borné par
   `DELAI_REDIS` (0,5 s par défaut, comme le catalogue), sans nouvelle tentative côté client ;
   ajouter la réponse 503 au contrat (et à `docs/contrats/billets.yaml`).
10. **Redis injoignable pendant `listerPlaces`.** `disponible` ne peut plus être calculé.
    Recommandation : `503` avec le même code que Q9 plutôt que des places affichées
    disponibles à tort ; contrat à compléter.
11. **Base injoignable** sur `listerPlaces` et `verrouillerPlace`. Recommandation : `503
    BASE_INDISPONIBLE` borné par `DELAI_BASE`, comme le catalogue (décision Q15 de BIL-004) ;
    contrat à compléter.
12. **Ordre des contrôles de `verrouillerPlace`.** Recommandation : 401 (jeton) → 403 (scope) →
    422 (identifiant, corps) → 404 `SEAT_NOT_FOUND` (place absente de la séance, lu en base) →
    409 `SEAT_ALREADY_TAKEN` si un billet existe (lu en base) → verrou Redis (`SET NX PX` ou
    script Lua). Une place inconnue répond donc 404 même si une clé Redis existe ; le contrôle
    du billet avant le verrou n'est pas un « lire puis écrire » dangereux, car
    `uq_billets_place` garantit le reste.
13. **Place d'une séance annulée.** La table `seances_annulees` et le consommateur
    `ticketing.show.cancelled` ne sont pas dans ce ticket. Recommandation : hors périmètre ; le
    verrou est accordé, le refus se fera à l'émission (ticket de `order.confirmed`). Aucun cas
    ici.
14. **Billet `ANNULE`.** Le modèle dit « `disponible` : ni verrou, ni billet sur la place » et
    `uq_billets_place` ne filtre pas le statut. Recommandation : toute ligne de `billets` rend la
    place indisponible (409 au verrouillage, `disponible` false), quel que soit son statut.
15. **Appel `confirmation: false` sur un verrou déjà confirmé (1 h).** Le contrat dit « prolonge
    le verrou » sans dire si une prolongation peut raccourcir. Recommandation : ne jamais
    raccourcir (le script Lua pose `max(PTTL restant, durée demandée)`) ; `expire_le` rend la fin
    réelle. Un nouvel appel `confirmation: true` du détenteur repose 1 h (200).
16. **Calcul de `expire_le`.** Recommandation : horloge du service à l'instant de la requête plus
    la durée réellement posée (PTTL rendu par le script), en UTC avec fuseau ; les tests tolèrent
    2 s d'écart.
17. **« Réservé au client `services` » (décision Q3).** Recommandation : contrôle par le seul
    scope `seats:lock` (`exige_scopes`), sans tester `azp` : le realm ne donne ce scope qu'à
    `services` (déjà prouvé par `tests/unit/test_realm_keycloak.py` et
    `tests/integration/test_keycloak.py`).
18. **Nouvelle publication de `ticketing.show.scheduled`** pour une séance déjà connue (autre
    `id` de message). Recommandation : aucune erreur, aucun doublon, aucune suppression
    (`INSERT ... ON CONFLICT DO NOTHING` sur la contrainte unique des places).
19. **Ordre « par rang, puis numéro ».** `rang` est un texte libre (`A`, `B`, `AA`, `10`).
    Recommandation : tri binaire (`COLLATE "C"`) sur `rang`, puis `numero` entier, puis `id`
    pour la stabilité ; documenté dans le README du service.
20. **Configuration.** Recommandation : `REDIS_URL` **obligatoire** pour billets (sans Redis, pas
    de verrou ; connexion paresseuse, aucun accès réseau au démarrage), `RABBITMQ_URL` facultatif
    (sans URL, pas de consommateur : tests unitaires), `DUREE_VERROU_RESERVATION` et
    `DUREE_VERROU_CONFIRMATION` entiers `> 0` (600 et 3600), `DELAI_REDIS` et `DELAI_BASE` comme
    le catalogue ; `compose.yaml` (`billets-env`) gagne `REDIS_URL`, `RABBITMQ_URL` et
    `depends_on: redis, rabbitmq` ; `test_squelettes_gateway.py` pose seulement `REDIS_URL`
    (aucun appel Redis sur `/health`).
21. **Santé et Redis.** Recommandation : `/health` ne dépend que de la base, comme le catalogue
    (Redis est partagé : retirer toutes les instances de Consul n'aiderait pas).
22. **Nom des contraintes.** Recommandation : `uq_places_seance_rang_numero` sur `places`,
    `uq_billets_place` sur `billets (seance_id, place_id)` (nom du modèle), `fk_billets_place`
    vers `places.id` ; colonnes de `billets` conformes au modèle dès ce ticket, la table restant
    vide jusqu'au ticket d'émission.
23. **Smoke test qui pose un verrou** sur la plateforme locale. Aucune route ne le lève
    (décision Q2) : la place reste prise 10 min. Recommandation : oui, sur une place de séance
    du jeu `make demo`, avec une `commande_id` aléatoire ; le test est ignoré si aucune place
    n'est disponible.
24. **Forme du test de concurrence.** Recommandation : 50 requêtes `PUT .../lock`, 50 commandes
    différentes, lancées par `asyncio.gather` et réparties sur deux instances de l'application
    (même base, même Redis) ; pas de variante par la gateway (déjà couverte pour la
    répartition par `test_squelettes_gateway.py`).
