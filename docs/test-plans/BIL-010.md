## Questions

> **Réponses (2026-11-13)** : les six recommandations ci-dessous sont retenues telles quelles
> (délégation du développeur). Hypothèses H1 à H6 validées. Aucune question ouverte.

1. **Période du cycle et durée du verrou de la tâche.** Ni le ticket ni les docs ne donnent de
   valeurs ni de noms. Recommandation : `EXPIRATION_PERIODE` (secondes, défaut 30, `gt=0`) dans
   la configuration de Commandes ; verrou Redis `commandes:tache:expiration`, valeur = nom de
   l'instance (`INSTANCE`), `SET NX PX` avec une durée égale à la période, **non relâché** en fin
   de cycle (il expire seul) : une seule exécution par fenêtre de période, même si les horloges
   des deux instances sont décalées. Tests : période 1 s.
2. **Redis injoignable au moment de prendre le verrou de la tâche.** Recommandation : cycle
   sauté, journal `WARNING`, aucune exécution sans verrou (la sûreté reste assurée par la base,
   mais CA2 demande une exécution par cycle).
3. **Où Billets libère les verrous.** BIL-009 a choisi `apres_commit` (au mieux, échec Redis
   journalisé). Pour `order.expired`, il n'y a aucun effet en base à protéger, et un verrou de
   confirmation oublié bloque la place jusqu'à 1 h. Recommandation : libérer **dans le
   traitement** ; `VerrouIndisponible` lève une exception, d'où trois tentatives puis
   `billets.order-expired.dlq`. Le rejeu après un commit raté relibère sans effet (comparer
   puis supprimer). Sinon, s'aligner sur BIL-009 (`apres_commit`) et adapter les cas
   `(dépend de Q3)`.
4. **Commande `EN_ATTENTE` dont `expire_le` est NULL** (réservation de `creerCommande`
   interrompue par un arrêt de l'instance). Elle n'a pas d'échéance d'après le modèle.
   Recommandation : hors périmètre de BIL-010, ignorée par la tâche, limite ajoutée au README de
   Commandes ; un cas vérifie qu'elle n'est pas touchée.
5. **Taille de lot par cycle.** Recommandation : au plus `EXPIRATION_LOT` commandes par cycle
   (défaut 100), par `expire_le` croissant ; le reste au cycle suivant.
6. **Limite connue du README (débit sans remboursement si une expiration croise le `POST` de
   paiement).** Recommandation : ne pas la traiter dans BIL-010 (ticket de remboursement) ;
   avec la revérification d'`expire_le` sous verrou de ligne (hypothèse H3), la tâche ne peut
   pas la provoquer, et un cas de concurrence le prouve. Le README le précise.

Hypothèses retenues (réponse dans les docs) :

- **H1** : l'échéance est `expire_le` (modèle : fin du plus court des verrous). Le « délai en
  configuration » est donc la durée des verrous de Billets (`duree_verrou_reservation`,
  `duree_verrou_confirmation`, déjà configurables), plus la période du cycle (Q1). Les tests
  les raccourcissent à 2 s (comme `test_expiration_verrous_postgres_redis.py`) et à 1 s.
- **H2** : une commande est dépassée si `expire_le <= maintenant` (le verrou Redis a disparu à
  cet instant).
- **H3** : la transition relit la commande sous `FOR UPDATE` et n'a lieu que si elle est encore
  `EN_ATTENTE` **et** `expire_le <= maintenant` relu sous ce verrou ; sinon un `payerCommande`
  qui vient de repousser `expire_le` (reverrouillage en confirmation) serait expiré pendant son
  `POST` de paiement.
- **H4** : la tâche réutilise `_expirer` de BIL-008 avec le client Paiements : lecture du
  paiement si `paiement_demande` (`lirePaiement`, jamais de `POST`), `remboursement_du: true`
  s'il est `ACCEPTE`, rien pour `REFUSE`, `REMBOURSE` ou 404 ; Paiements injoignable : commande
  laissée `EN_ATTENTE`, reprise au cycle suivant. Une erreur sur une commande n'interrompt pas
  le cycle.
- **H5** : Billets consomme par `consommateur_idempotent`, file `billets.order-expired`, libère
  toutes les `place_ids` par le script « comparer puis supprimer » existant
  (`VerrousRedis.liberer`) et ignore `remboursement_du`.
- **H6** : Commandes reçoit `REDIS_URL` (Compose), obligatoire, comme Billets.
