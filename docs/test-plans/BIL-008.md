# Plan de test : BIL-008, US3 : passer commande et payer

- Ticket : `docs/tickets/BIL-008.md` (section « Décisions (validation du contrat, 2026-11-03) »,
  Q1 à Q12, qui fait foi sur la page Notion) ; contrats : `services/commandes/openapi.yaml`
  (`creerCommande`, `listerCommandes`, `lireCommande`, `payerCommande`),
  `services/paiements/openapi.yaml` (`creerPaiement`), recopiés de `docs/contrats/` ;
  événements : `docs/evenements/ticketing.order.confirmed.json`, `ticketing.order.expired.json` ;
  modèle : `docs/modele-donnees.md` (Commandes, Paiements)
- Niveaux : unitaire (dont `pytest -m contract`, sans Docker), intégration (Testcontainers :
  PostgreSQL 16, Redis 7, RabbitMQ ; Consul et Traefik pour un seul cas)

Ticket back : ni `composant` ni `parcours`. Il touche Commandes et les places : CA1 et le plafond
portent des cas de concurrence en intégration (vraies requêtes simultanées, `asyncio.gather`).
Les décisions gardent leurs numéros (« décision Q1 ») ; les questions du plan partent de **Q13**.
Les sections E1 à E10 sont des critères dérivés des décisions, du contrat et des rules.

### Doubles et fixtures

- **Unitaire** : application Commandes sans lifespan, dépôt en mémoire, Billets, Catalogue et
  Paiements simulés par `httpx.MockTransport` passé à `ClientService(transport=...)` (le double
  enregistre chaque requête : méthode, chemin, corps, en-têtes) ; Paiements testé seul avec dépôt
  en mémoire.
- **Intégration (choix retenu)** : vrais services en ASGI pour **Billets** (vrai Redis, sa base)
  et **Paiements** (sa base), branchés sur les `ClientService` de Commandes par
  `httpx.ASGITransport` : la concurrence et l'idempotence se prouvent sur le vrai code, sans
  simulacre de base. **Catalogue** : double ASGI minimal qui rend une `Seance` validée contre le
  schéma du contrat catalogue (programmable : 404, `annulee`, `debut` passé, panne). **Keycloak** :
  `MockTransport` qui sert à `JetonService` un jeton `EmetteurDeTest` (`client="services"`,
  `scopes=["seats:lock","payments:write"]`). Un conteneur PostgreSQL, trois bases (`commandes`,
  `paiements`, `billets`) migrées par `alembic upgrade head` ; `commandes_1` et `commandes_2` :
  deux applications Commandes sur la même base.
- **Panne simulée** : transport enveloppe autour de l'`ASGITransport` de Paiements, qui laisse
  passer la requête puis lève `httpx.ReadTimeout` (réponse perdue) ou `ConnectError`.

## Questions

> **Réponses (2026-11-03)** : recommandations Q13 à Q25 retenues (délégation des validations). Q18 complète le 503 de `payerCommande` dans les deux contrats ; Q22 ajoute `email` à `commun.auth.Appelant`.

13. **Montant des lignes.** Le modèle crée commande et lignes (montants) avant les verrous, mais
    la catégorie d'une place n'est connue que par la réponse `Verrou` (`categorie_id`).
    Recommandation : commande `EN_ATTENTE` créée d'abord, montant de chaque ligne fixé à la
    réponse de son verrou (prix de la catégorie dans la séance lue), `montant_total` écrit dans
    la même transaction ; les tests ne vérifient que le résultat.
14. **Ordre des contrôles de `creerCommande`.** Recommandation : 401, 403, 422, clé
    d'idempotence, séance lue dans Catalogue (404 `SHOW_NOT_FOUND`, 409 `SHOW_CANCELLED`,
    `SHOW_ALREADY_STARTED` si `debut` ≤ maintenant), plafond, création `EN_ATTENTE`, verrous de
    réservation, reverrouillage, Paiements. Un refus avant la création ne crée aucune commande.
15. **Plafond.** Recommandation : refus si lignes `EN_ATTENTE` + `CONFIRMEE` existantes +
    places demandées > limite (égalité acceptée) ; refus sans commande, sans verrou ni événement.
16. **`Idempotency-Key` de `creerCommande`.** Recommandation : verrou consultatif de session sur
    (`client`, clé) tenu pendant toute la requête ; s'il est pris : 409 `REQUEST_IN_PROGRESS` ;
    sinon une commande existante (`UNIQUE (client, cle_idempotence)`) est rendue en 200 dans son
    état courant (`CONFIRMEE`, `EXPIREE` après 402, `EN_ATTENTE` après 503), corps ignoré.
17. **409 de Paiements vu par Commandes.** Recommandation : `SHOW_CANCELLED` : 409
    `SHOW_CANCELLED`, commande `EXPIREE` et `ticketing.order.expired` (sans débit) ;
    `PAYMENT_ALREADY_EXISTS` (montant figé, ne devrait pas arriver) : journalisé, 503
    `SERVICE_INDISPONIBLE`, commande `EN_ATTENTE`.
18. **Billets indisponible.** Recommandation : pendant les verrous de réservation : 503, commande
    `EXPIREE` et `ticketing.order.expired` ; pendant le reverrouillage (deux routes) : 503,
    commande `EN_ATTENTE`, nouvel essai par `payerCommande` ; ajouter Billets au 503 de
    `payerCommande` dans les deux contrats.
19. **404 de Billets (`SEAT_NOT_FOUND`)** et contenu de `place_ids` de `order.expired`.
    Recommandation : 404 `SEAT_NOT_FOUND`, commande `EXPIREE`, `order.expired` ; `place_ids` =
    toutes les places de la commande (Billets ne libère que les verrous qu'elle détient).
20. **Paiements, séance annulée.** Recommandation : un paiement déjà enregistré se rejoue d'abord
    (résultat enregistré) ; sinon 409 `SHOW_CANCELLED` sans ligne `paiements`.
21. **Paiements simultanés de même clé et même corps.** Recommandation : tous 201 avec le même
    `id` (`INSERT ... ON CONFLICT DO NOTHING` puis relecture), jamais 409 ni 500.
22. **E-mail de l'acheteur.** `commun.auth.Appelant` n'a pas d'e-mail. Recommandation : champ
    `email` (claim `email`, `None` si absent) ajouté à `Appelant` ; `NULL` pour un revendeur.
23. **Configuration.** Recommandation : Commandes : `URL_GATEWAY` (`http://traefik`),
    `URL_JETON` Keycloak, `SERVICES_CLIENT_SECRET` (`.env`, vide dans `.env.example`),
    `LIMITE_BILLETS_PAR_SEANCE` entier > 0 (10), `RABBITMQ_URL` facultatif (relais d'outbox) ;
    Paiements : rien de nouveau ; `compose.yaml` (`commandes-env`) complété.
24. **Libération des places par Billets à `order.expired`.** Aucun consommateur côté Billets
    n'est dans le périmètre (service non listé). Recommandation : hors périmètre ; les places
    restent verrouillées jusqu'à leur expiration ; ce plan teste seulement la publication.
25. **`/api/v1/payments` derrière Traefik.** Recommandation : exposé (préfixe `payments`) comme
    les autres services, protégé par `payments:write` ; un jeton client reçoit 403.
