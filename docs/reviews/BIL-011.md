## Vérifications faites sans constat

- **Un seul remboursement par paiement accepté** : chaque passage `ACCEPTE` → `REMBOURSE` est un
  `UPDATE … WHERE statut = 'ACCEPTE' RETURNING` (`paiements/infra/depot.py:141`, `:155`). Deux
  transactions sur la même ligne s'attendent et la seconde réévalue la condition après le commit
  de la première, sans rien renvoyer. Un `payment.refunded` est publié pour chaque ligne
  renvoyée, dans la même transaction (outbox) que `messages_traites`. La règle tient quel que soit
  l'ordre `show.cancelled` / `ticket.rejected` et en cas de livraisons en double (même `id` :
  `messages_traites` ; autre `id` : condition sur le statut). Les deux `show.cancelled` d'une même
  séance sont en plus sérialisés par le verrou exclusif.
- **Aucun débit sans remboursement** : `payer` prend le verrou partagé avant de lire
  `seances_annulees`, dans la transaction ouverte par `lire_par_commande`. Ce verrou est tenu
  jusqu'au `commit` de `inserer_ou_relire`, ou jusqu'au rollback à la fermeture de la session
  après un 409. Le consommateur prend le verrou exclusif avant d'inscrire la séance et de
  rembourser. En READ COMMITTED, chaque instruction exécutée après le verrou voit les écritures
  commitées. Pas d'interblocage : `payer` ne touche ni `messages_traites` ni plusieurs lignes, et
  `ticket.rejected` ne modifie qu'une ligne. Aucune collision de clé avec d'autres verrous
  consultatifs (Paiements et Billets n'en avaient pas ; Commandes n'utilise pas `verrou_seance`).
- **Aucun billet `EMIS` sur une séance annulée** : le verrou partagé est pris dans
  `emettre_commande` avant la lecture de `seances_annulees`, et le verrou exclusif dans
  `annuler_seance`, avant l'`UPDATE billets … WHERE statut = 'EMIS'`. Comme `emettre` fonctionne
  par `ON CONFLICT DO NOTHING`, sans SAVEPOINT, aucune perte de verrou n'est possible.
  `uq_billets_place` est inchangée et les billets `ANNULE` gardent leur place.
- **Annulation dans Catalogue** : contrôle du rôle `admin` puis du scope `events:write`
  (`routes.py:225`) ; ordre 404, puis 409 `SHOW_ALREADY_CANCELLED`, puis `SHOW_ALREADY_STARTED` ;
  `UPDATE … WHERE annulee = false RETURNING` et outbox dans la même transaction ; 0 ligne
  modifiée → rollback et 409. Le cache est invalidé après le commit : nouvelle génération pour
  `seance:<id>` (copies fraîche et de secours des deux lectures de détail) et pour
  `seances:<evenement_id>`. Les contrats `services/catalogue/openapi.yaml` et
  `docs/contrats/catalogue.yaml` sont alignés (503 compris).
- **Transitions de Commandes** : `EN_ATTENTE` → `EXPIREE` + `order.expired` sans
  `remboursement_du`, sous `FOR UPDATE` trié par `id`, la condition étant réévaluée après
  attente ; `CONFIRMEE` → `REMBOURSEE` ; `EN_ATTENTE` → `EXPIREE` sur `payment.refunded` (Q4) ;
  `EXPIREE`/`REMBOURSEE` ignorées (`INFO`) ; commande inconnue ignorée (`WARNING`). `REMBOURSEE`
  n'entre pas dans `STATUTS_COMPTES`. Tout est conforme à `docs/modele-donnees.md`.
- **Notifications** : un e-mail d'annulation par commande (`uq_envois_evenement_commande`,
  inscription avant l'appel SMTP, une transaction par commande) ; revendeur sans adresse ignoré ;
  `CommandeInconnue` pour `payment.refunded` ; journaux limités aux identifiants. Les limites Q6
  sont écrites dans le README.
- **Compose** : `RABBITMQ_URL` ajouté à l'ancre `paiements-env` et `depends_on rabbitmq healthy`
  sur `paiements-1`, sur le même modèle que les autres services ; la valeur vient de `.env`,
  aucun secret dans le dépôt.
