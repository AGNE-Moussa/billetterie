# BIL-009 : US4 : recevoir son billet par e-mail

- **Branche** : `feat/bil-009-emission-billets` (empilée sur `feat/bil-008-commande-paiement`,
  dérogation du développeur du 2026-11-12 : BIL-008 en IN REVIEW, merge bloqué par le compte
  GitHub verrouillé ; PR avec base `feat/bil-008-commande-paiement`)
- **Dépend de** : BIL-008
- **Service** : notifications, billets

## Objectif

En tant que client, je veux recevoir mes billets avec un QR code par e-mail dès le paiement
confirmé.

## Étapes

- [ ] Billets consomme `ticketing.order.confirmed`, passe les places en vendues, émet les billets
  (QR code signé) et publie `ticketing.ticket.issued`.
- [ ] Générer le service `notifications` ; il consomme `ticketing.ticket.issued` et envoie
  l'e-mail.
- [ ] Serveur SMTP de test (Mailpit) dans le compose pour voir les e-mails.
- [ ] Historique d'envoi pour ne jamais envoyer deux fois le même e-mail.

## Critères d'acceptance

| #   | Critère                                                    |
| --- | ---------------------------------------------------------- |
| CA1 | Un paiement confirmé produit un e-mail visible dans Mailpit |
| CA2 | Le QR code contient un identifiant signé, vérifiable par Billets |
| CA3 | Un événement reçu deux fois ne produit qu'un e-mail         |

## Contraintes

- Aucune adresse e-mail réelle dans les données de test.

## Décisions (validées d'avance, recommandations du 2026-11-12)

- Contrat : aucune route HTTP. CA2 est tenu par une fonction de domaine de Billets
  `verifier_qr(contenu) -> billet_id` (HMAC recalculé, clé lue dans l'environnement) ; la route
  de scan relève de la V3.
- Adresse e-mail : on suit `docs/modele-donnees.md` (section Notifications). Notifications
  consomme aussi `ticketing.order.confirmed` et tient `destinataires_commande` (`email` NULL =
  revendeur, rien à envoyer) ; un `ticket.issued` dont la commande est encore inconnue lève une
  exception (nouvel essai). `ticketing.ticket.issued` v1 reste inchangé.
- Un e-mail par `ticket.issued` (donc par billet) ; anti-doublon : table `envois`,
  `UNIQUE (evenement_id, commande_id)` comme le modèle (CA3).
- Place déjà vendue ou séance annulée au moment de l'émission : on suit `docs/conception.md` §5
  et `docs/modele-donnees.md` l. 120-127 : émission tout ou rien par commande (savepoint), aucun
  billet, `ticketing.ticket.rejected` publié par l'outbox. Les consommateurs de
  `ticket.rejected` (remboursement par Paiements, e-mail de refus) sont hors de BIL-009.
- H6 (écart assumé au modèle) : pas de clé étrangère `destinataires_commande.seance_id` vers
  `infos_seances`, remplie seulement par `show.scheduled` (hors ticket) ; sinon tout
  `order.confirmed` finirait en DLQ.
- Implémentation : pas de savepoint pour le tout ou rien (il casserait « même transaction »
  sous PostgreSQL) ; suppression des billets insérés dans la même transaction ; modèle mis à
  jour. Verrous libérés après le commit, même pour un message déjà traité (comparer puis
  supprimer). Course `seances_annulees` lue puis billets écrits : à traiter par le consommateur
  de `show.cancelled` (hors ticket, billets passés `ANNULE`).
- Questions Q2 à Q11 du plan : recommandations du test-planner retenues, sauf contradiction
  avec `docs/modele-donnees.md`, qui l'emporte.
