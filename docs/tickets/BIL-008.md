# BIL-008 : US3 : passer commande et payer

- **Branche** : `feat/bil-008-commande-paiement`
- **Dépend de** : BIL-006
- **Service** : commandes, paiements

## Objectif

En tant que client, je veux transformer mes places verrouillées en commande et la payer, afin
d'obtenir mes billets.

## Étapes

- [ ] Partir des squelettes `commandes` et `paiements` créés en BIL-001.
- [ ] Commandes : création d'une commande en attente à partir des places verrouillées
  (vérification auprès de Billets).
- [ ] Plafond de billets par client et par séance.
- [ ] Paiements : paiement simulé (succès ou refus configurable), clé d'idempotence obligatoire.
- [ ] Succès : commande confirmée et événement `ticketing.order.confirmed` via l'outbox.

## Critères d'acceptance

| #   | Critère                                                                 |
| --- | ----------------------------------------------------------------------- |
| CA1 | Une commande ne peut porter que des places verrouillées par le même client |
| CA2 | Rejouer un paiement avec la même clé ne débite pas deux fois            |
| CA3 | Un paiement accepté publie `ticketing.order.confirmed`                  |

## Contraintes

- Appels inter-services uniquement via le client HTTP de `libs/commun` (BIL-F12).

## Décisions (validation du contrat, 2026-11-03)

Recommandations retenues (délégation des validations) :

  page Notion.
- Q2 : CA1 = une commande ne porte que des places verrouillées à son profit ; place verrouillée
  par une autre commande ou vendue : 409 `SEAT_ALREADY_TAKEN`, commande `EXPIREE`,
  `ticketing.order.expired` ; testé en concurrence (deux clients, même place).
- Q3 : `LIMITE_BILLETS_PAR_SEANCE` (défaut 10), lignes `EN_ATTENTE` et `CONFIRMEE` comptées sous
  `pg_advisory_xact_lock(client, seance_id)`, 409 `TICKET_LIMIT_EXCEEDED`.
- Q4 : seul Commandes appelle Paiements (`creerCommande`, `payerCommande`), par
  `commun.http.ClientService` avec `JetonService` (`payments:write`).
- Q5 : refus simulé par la carte de test (`4000000000000002` refusée), sans variable globale.
- Q6 : `Idempotency-Key` = `commande_id`, `UNIQUE (commande_id)` ; même clé et même
  (`seance_id`, `montant`) : rejeu (résultat enregistré, aucun nouveau débit) ; sinon 409
  `PAYMENT_ALREADY_EXISTS`.
- Q7 : `listerCommandes` et `lireCommande` font partie du ticket.
- Q8 : hors périmètre : expiration à l'échéance, consommateurs `show.cancelled`,
  `ticket.rejected`, `payment.refunded`, émission des billets. Dans le périmètre :
  `ticketing.order.expired` (outbox) dans les trois cas synchrones (verrou refusé, place perdue,

- Q9 : table `seances_annulees` de Paiements créée vide ; `SHOW_CANCELLED` testé par insertion.
- Q10 : `503 BASE_INDISPONIBLE` ajouté à `creerPaiement` et aux routes de Commandes (contrats des
  services et contrats cibles).
- Q11 : BIL-003 et BIL-004 sont `✅ DONE` ; `JetonService` existe (`libs/commun/http.py`).
- Q12 : alias `Idempotency-Key` (UUID obligatoire côté Paiements, `str | None` ≤ 100 côté

## Décisions (implémentation, 2026-11-03)

- Décisions hors plan de l'implémenteur acceptées : rejeu d'une commande sans montant ni échéance
  (`montant` 0, `expire_le` = `cree_le`) ; erreur imprévue pendant les verrous de réservation :
  commande `EXPIREE` et `order.expired` ; confirmation concurrente sans second `order.confirmed` ;
  lignes lues par `place_id` ; verrous de Billets en une seule tentative.
- `payerCommande`, séance inconnue de Catalogue : 404 `SHOW_NOT_FOUND`, description du 404
  complétée dans les deux contrats.
- `payerCommande`, séance annulée ou commencée d'après Catalogue : 409, commande `EXPIREE` et
  `ticketing.order.expired` (comme Q17).

## Décisions (review, 2026-11-03)

- Point 1 (bloquant) : transitions de statut gardées (`WHERE statut = 'EN_ATTENTE'` ou
  `FOR UPDATE`), dans `_confirmer_et_payer` et `fixer_montants` ; aucun appel à Paiements si la
  transition échoue ; jamais de second `order.confirmed`.
- Point 2 (développeur) : `payerCommande` sur une réservation encore en cours (`expire_le` NULL) :
  409 `REQUEST_IN_PROGRESS`, ajouté au 409 de `payerCommande` dans les deux contrats.
- Point 3 (développeur) : avant d'expirer une commande déjà envoyée à Paiements, Commandes rejoue
  la clé (idempotent) ; si le paiement est `ACCEPTE`, `ticketing.order.expired` porte
  `remboursement_du: true` (champ facultatif ajouté au schéma, version 1, aucun consommateur
  existant) ; le remboursement relève d'un ticket ultérieur.
- Point 4 : la connexion de la clé d'idempotence n'est pas tenue pendant les appels HTTP (ou
  attente du pool bornée par `delai_base`).
- Point 5 : tests de concurrence sur une même commande (`creerCommande` contre `payerCommande`,
  deux `payerCommande`).
- Suggestions : listées dans la PR.
- Point 3, suite : nouvelle route de lecture `GET /api/v1/payments/{commande_id}` (`lirePaiement`,
  scope `payments:write`, client `services` seulement ; 200 `Paiement`, 404 `PAYMENT_NOT_FOUND`,
  401, 403, 422, 503 `BASE_INDISPONIBLE`) : avant d'expirer une commande déjà envoyée à
  Paiements, Commandes **lit** le paiement (jamais de `POST`, donc aucun débit possible) ;
  `ACCEPTE` ⇒ `remboursement_du: true`.
- Point 4, suite : pool des clés d'idempotence de 5 connexions sans débordement (le PostgreSQL est
  partagé par tous les services).
- Paiements injoignable pendant la lecture avant expiration : 503 `SERVICE_INDISPONIBLE`, commande
  laissée `EN_ATTENTE` (aucun remboursement dû perdu).
- Colonne `commandes.paiement_demande` (ajoutée à 0003, non mergée), posée au passage
  `EN_ATTENTE` juste avant le POST ; marquage implicite dans `changer_statut`, documenté.
- Course restante (expiration pendant le POST d'une autre requête) : journal d'erreur et limite
  écrite dans le README ; à traiter avec le ticket de remboursement (ticket de suivi).
- Seconde passe : point 9 (limite écrite dans le README) corrigé par l'orchestrateur ; points 10
  à 13 listés dans la PR.
