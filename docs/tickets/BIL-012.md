# BIL-012 : US7 : API pour les revendeurs partenaires

- **Branche** : `feat/bil-012-api-partenaires` (empilée sur `feat/bil-010-expiration`, chaîne
  #42 BIL-008 ← #43 BIL-009 ← #44 BIL-010 ; dérogation du développeur du 2026-11-12, compte
  GitHub verrouillé ; PR avec base `feat/bil-010-expiration`)
- **Dépend de** : BIL-008
- **Service** : commandes (et catalogue, billets en lecture, Traefik)

## Objectif

En tant que revendeur partenaire, je veux consulter les événements et vendre des billets pour
mon compte via l'API.

## Étapes

- [ ] Rattacher chaque commande à son canal (client direct ou partenaire).
- [ ] Routes partenaires : lecture du catalogue et de la disponibilité, création et suivi de
  ses commandes.
- [ ] Filtre systématique sur l'identifiant du partenaire issu du jeton.
- [ ] Limitation de débit dédiée aux partenaires dans Traefik.
- [ ] Documentation OpenAPI partenaires publiée séparément.

## Critères d'acceptance

| #   | Critère                                                      |
| --- | ------------------------------------------------------------ |
| CA1 | Un partenaire ne voit jamais les commandes d'un autre (test dédié) |
| CA2 | Le parcours complet partenaire passe dans Postman            |
| CA3 | Au-delà du quota, le partenaire reçoit 429                   |

## Contraintes

- Flux Client Credentials uniquement pour les partenaires.

## Décisions (validées d'avance, recommandations)

- Contrat : aucune route dédiée ; les routes existantes servent le rôle `partner`, filtrées par
  l'appelant. Documentation séparée : `docs/contrats/partenaires.yaml` (opérations recopiées à
  l'identique, `429` en plus, sécurité `HTTPBearer`, flux Client Credentials décrit en
  introduction) ; ligne ajoutée à `docs/conventions.md` et à `.claude/rules/contrats-api.md`.
  Aucune modification de `services/*/openapi.yaml`.
- Q1 : hôte Traefik dédié aux partenaires (mêmes chemins `/api/v1/...`) sur la chaîne existante
  `partenaires@file` (5/s, rafale 10, par `Authorization`).
- Q2 : la vérification du jeton côté gateway refuse le rôle `partner` sur la chaîne `standard`
  (`403 ROLE_MANQUANT`) : un partenaire ne contourne pas son quota.
- Q3 : canal de la commande en base seulement (`DIRECT` / `PARTENAIRE`, déduit du rôle du
  jeton), pas exposé dans l'API ; modèle de données à mettre à jour.
- Q4 : lecture des billets hors périmètre (routes `/tickets` pas encore codées).
- Q5 : lieux inclus (`listerLieux`, `lireLieu`).
- Q6 : routes publiques sans `security` (introduction : « envoyez toujours votre jeton ») ; 429
  au corps non normalisé ; `Retry-After` à confirmer par le test de CA3.
- Q7 : document écrit à la main + test qui vérifie chaque opération contre son service (429 en
  plus) ; le test `test_chaque_service_metier_a_son_contrat_cible` doit exclure `partenaires`.
- Q8 : `HTTPBearer`.
- Plan (`docs/test-plans/BIL-012.md`, 48 cas) : hôte `HOTE_PARTENAIRES` (`partenaires.localhost`
  en local, alias réseau sur Traefik pour Newman) ; jeton sans rôle `partner` refusé sur l'hôte
  partenaires (403 `ROLE_MANQUANT`) ; migration `0005` du canal (`PARTENAIRE` si `email IS NULL`,
  sinon `DIRECT`, puis `NOT NULL` et `ck_commandes_canal`) ; un jeton `customer` + `partner`
  donne le canal `PARTENAIRE`. CA2 en smoke (Newman), CA3 en intégration (vrai Traefik).
- Squelette : `postman/` est hors du périmètre de tous les agents : la collection
  `postman/partenaires.json` (squelette puis contenu) et le smoke test Newman sont écrits par
  l'orchestrateur, comme les smoke tests. Colonne `canal` et migration 0005 posées à
  l'implémentation. Vérificateur : `/verifier` (chaîne standard), `/verifier/partenaires`.
  Règle `contrats-api.md` ramenée à 30 lignes.
- Tests : rouge mesuré (unitaires `19 failed, 44 passed`, intégration `11 failed, 12 passed`) ;
  les verts d'isolation viennent de BIL-008 (régression CA1). `NotImplementedError` du squelette
