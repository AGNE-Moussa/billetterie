# BIL-011 : US6 : annuler une séance et rembourser les clients

- **Branche** : `feat/bil-011-annulation` (empilée sur `feat/bil-012-api-partenaires`, chaîne
  #42 BIL-008 ← #43 BIL-009 ← #44 BIL-010 ← #45 BIL-012 ; dérogation du développeur du
  2026-11-12, compte GitHub verrouillé ; PR avec base `feat/bil-012-api-partenaires`)
- **Dépend de** : BIL-009
- **Service** : paiements (et catalogue, commandes, billets, notifications)

## Objectif

En tant qu'organisateur, je veux annuler une séance et que tous les acheteurs soient remboursés
et prévenus automatiquement.

## Étapes

- [ ] Catalogue : route admin d'annulation qui publie `ticketing.show.cancelled`.
- [ ] Commandes : passe les commandes de la séance en annulées.
- [ ] Paiements : rembourse chaque transaction et publie `ticketing.payment.refunded`.
- [ ] Notifications : e-mail d'annulation et de remboursement.

## Critères d'acceptance

| #   | Critère                                                              |
| --- | -------------------------------------------------------------------- |
| CA1 | Toutes les commandes payées de la séance sont remboursées une seule fois |
| CA2 | Chaque acheteur reçoit un e-mail d'annulation                        |
| CA3 | Les billets de la séance deviennent invalides                        |

## Contraintes

- Seul le rôle `admin` peut annuler une séance.

## Décisions (validées d'avance, recommandations)

- Contrat : route `annulerSeance`, `POST /api/v1/events/{evenement_id}/shows/{seance_id}/cancellation`
  (scope `events:write`, rôle admin, sans corps), recopiée du contrat cible avec 503
  `BASE_INDISPONIBLE` ajouté aux deux fichiers. 200 `Seance` (champ `annulee` déjà présent),
  409 `SHOW_ALREADY_CANCELLED` (testé d'abord) ou `SHOW_ALREADY_STARTED`, 404 si la séance
  n'appartient pas à l'événement. Aucune autre route ; le reste passe par les événements
  (`show.cancelled`, `payment.refunded`, schémas existants).
- Annulation concurrente : `UPDATE ... WHERE annulee = false` et outbox dans la même transaction ;
  0 ligne : 409. Cache Redis des lectures (BIL-005) invalidé après le commit. Séances annulées
  gardées dans `listerSeances` ; pas de date d'annulation dans `Seance`.
- Plan (`docs/test-plans/BIL-011.md`, 60 cas dont 9 de concurrence) : Q1-Q8 et H1-H7 retenues.
  Le modèle l'emporte sur le ticket (`CONFIRMEE` → `REMBOURSEE` à `payment.refunded`,
  `EN_ATTENTE` → `EXPIREE` sans appel à Paiements). Consommateur `ticket.rejected` de Paiements
  inclus (remboursement ; e-mail de refus hors ticket). Courses paiement/annulation et
  émission/annulation : verrou consultatif PostgreSQL sur la séance dans chaque service
  (partagé pour payer ou émettre, exclusif pour annuler). `payment.refunded` sur une commande
  `EN_ATTENTE` : `EXPIREE` + `order.expired`. Un e-mail d'annulation par commande. Limite
  écrite au README de Notifications (acheteur confirmé après l'annulation). `remboursement_du`
  sur `order.expired` : ticket de suivi.
- Mode allégé (2026-11-14, développeur) : tests d'intégration écrits en fin de parcours ; ceux
  déjà écrits sont mis de côté dans le dossier temporaire de la session. Tests unitaires du plan
  conservés (verts). Test existant adapté : `tests/integration/test_squelettes_compose.py`
  (paiements dépend désormais de RabbitMQ).
- Test à adapter : `services/catalogue/tests/unit/test_contrat_cible.py` (vérifiait l'absence
  d'annulation ; 12 opérations).
